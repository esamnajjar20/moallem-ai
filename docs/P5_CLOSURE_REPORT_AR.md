**القرار: PARTIAL / NOT READY — أُغلقت الأعمال البرمجية الممكنة في نسخة التطبيق، لكن لا يمكن إعلان P5 مغلقة إنتاجياً دون اعتمادات المالك وخدمات البنية التحتية واختبار PostgreSQL فعلي.**

## 1. ملخص ما أُنجز في هذه الجولة

- إضافة `OpenAICompatibleHTTPProvider` كعميل HTTPS اختياري ومتوافق مع شكل Chat Completions، مع تثبيت مطابقة معرف النموذج، وحجم استجابة محدود، ومنع التحويلات وإعادة المحاولة التلقائية، وتصنيف النتيجة الملتبسة كـUNKNOWN.
- الإبقاء على `DenyAllAIExecution` كسياسة افتراضية؛ لم يتم تسجيل مزود فعلي ولم يُفتح تنفيذ AI.
- إضافة عملاء الخدمات الداخلية `HTTPQuarantineStorage` و`HTTPMalwareScanner` و`HTTPSandboxedExtractor`، مع دعم mTLS وتعطيل توريث proxy من البيئة ومنع التحويلات.
- تمرير `tenant_id` و`file_id` ومرجع التخزين مع كل طلب Scan/Extract؛ يجب على الخدمة البعيدة التحقق من تطابق ملكية الكائن قبل قراءته، ولا يجوز اعتبار مرجع التخزين تصريح وصول.
- تقييد التخزين إلى Buckets معتمدة صراحة، وإظهار فشل التنظيف وعدم اعتباره نجاحاً، والتحقق من هوية الفاحص وسياسة Sandbox. OCR ما زال معطلاً افتراضياً.
- جعل `httpx` اعتماد تشغيل أساسي لأنه مستخدم من محولات الخدمات الجديدة.
- معالجة حواجز بعض migrations التاريخية بحيث يمكن توليد SQL لكل السلسلة في وضع Alembic offline مع الاحتفاظ بفحوص البيانات داخل PostgreSQL `DO` blocks.
- إضافة توثيق عقد التكاملات، وتحديث حالة P5 لتفصل ما هو منفذ عن الاعتمادات والبيئة المفقودة.

## 4. ما أُغلق وما بقي

### أُغلق في كود التطبيق

- عميل HTTP لمزود AI متوافق مع عقد البوابة، دون تمكينه افتراضياً.
- عميل تخزين Quarantine خاص، وعميل فحص Malware، وعميل Sandbox Extraction.
- تمرير نطاق المؤسسة والملف لخدمات الفحص والاستخراج والتحقق منه في عقد الطلب.
- حواجز HTTPS وmTLS الاختيارية، allow-list للبكتات، حدود للاستجابات، ومنع redirects، ومنع OCR افتراضياً.
- توليد SQL الكامل لسلسلة migrations صعوداً ونزولاً في وضع offline.

### لا يمكن إغلاقه من الكود وحده دون اعتماد أو بنية تحتية

1. **P0-09 وADR-018:** اختيار مزود AI والنموذج الدقيق والإصدار والمنطقة وفئات البيانات المرسلة وشروط الخصوصية والتكلفة والجودة العربية. لا توجد موافقة مالك موثقة في الملفات.
2. **DEC-028:** اعتماد سياسة الاحتفاظ والحذف وإزالة الهوية للمدخلات والمخرجات والملفات والنص المستخرج والقياسات.
3. **DEC-029:** اعتماد مزود تخزين الكائنات والمنطقة ومفاتيح KMS والتشفير ودورة الحياة والحذف.
4. **Production Budget Authorizer:** لا يوجد بعد نظام دائم لحجز الميزانية وتسويتها وإعادة تسوية الحجوزات اليتيمة. `AIExecutionAuthorizer` عقد برمجي، و`DenyAllAIExecution` لا يسمح بأي استدعاء.
5. نشر خدمة التخزين، ومحرك فحص برمجيات خبيثة فعلي، وخدمة Parser داخل Sandbox حقيقي والتحقق من عزلها واختبارها. العملاء البرمجيون لا يثبتون وجود هذه الخدمات أو سلامتها.
6. اعتماد آلية تشغيلية لحالات مزود AI ذات النتيجة `UNKNOWN` دون إعادة تنفيذ عمياء قد تكرر التكلفة.
7. بناء مهمة reconciliation للكائنات اليتيمة وفشل حذفها؛ العميل يرفع خطأ التنظيف ولا توجد أدلة هنا على وجود عامل إنتاجي لهذه المهمة.
8. ربط الخدمات المعتمدة بمسارات API وWorker الفعلية، واختبار تدفق الصلاحيات والبيانات من البداية للنهاية.
9. تشغيل الاختبارات والترحيلات على Python 3.12.x وقاعدة PostgreSQL مؤقتة، بما فيها `alembic check` وupgrade/downgrade/re-upgrade واختبارات العزل والتزامن.
10. Embeddings وVector Index وترتيب نتائج الاسترجاع ليست منفذة هنا؛ بناء السياق الحالي يحفظ provenance لكنه ليس منصة RAG مكتملة.
